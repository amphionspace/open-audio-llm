# 问题 91：会议角色模式下办公室背景人声的「幻觉」（2026-10-30）

**结论（2026-10-31 复核后修订）：客户看到的「幻觉」主体是模型对远处、听不清的背景人声写出不稳定的文字 —— 设备 891 字里 85% 不是复读，33 段里约 2/3 独立模型（FireRedASR2-AED）听不出内容，base Qwen3-ASR 离线在同样片段上写得比设备还多（1489–1879 字）。复读是次要部分：设备上 5/33 段、每段 ≤58 字、占 15% 字数；离线整段解码（固定 512 token、无恢复）时复读才写到上限，部署运行时自 2026-10-20 起已按音频时长限制输出长度并对密集复读重解码。** 复读率高于 base 是 v3 三阶段 SFT 引入的回退，TS 几轮训练没有修掉。复核见文末「七、2026-10-31 复核」。

对象：客户设备上是 10.28 交付包（054 avg3 的前身 048 avg3），在 113 上用部署推理栈（vLLM 0.18.0，bf16，贪心，temperature 0）回放 048 avg3 与 054 avg3，并与 base `Qwen3-ASR-1.7B`、9.26 版本（34479）对照。没有训练。

数据：客户真机原音两段（s1 524.8 s、s2 339.9 s）切出 33 个「幻觉」片段 + 4 个对照片段（测试者本人清楚说话）。**客户保密数据，只在本机调试目录，不入库、不发布、不上传。** 片段边界取设备当时定稿的 `audio_range`。

## 一、背景里确实有人说话

| 口径 | s1 的 33 段中 | 说明 |
| --- | --- | --- |
| Silero VAD 语音占比 0.5–0.96 | 多数 | 不是纯噪声，是远处的人声对话 |
| VAD 占比 < 0.2 | 5 段（s2 的 seg09/10/30/35/41） | 这几段接近只有噪声 |
| 段内 95 分位电平 | −21～−35 dBFS | 测试者本人说话是 −15～−17 dBFS |

base `Qwen3-ASR-1.7B` 在同样片段上也会写出部分相同的词，说明「有声音可转写」不是我们模型独有的判断。所以**「会议角色模式下要不要转写非参会者的背景对话」是产品口径问题**，不是单纯的模型缺陷。

## 二、我们的模型会退化成复读

复读判定：去标点后同一 1–4 字单元连续重复 ≥ 8 次。每个模型对 33 段 × 2 种 prompt 形态 × 4 种边界偏移，**离线整段解码、`max_tokens` 512、没有运行时的长度预算和复读恢复**，所以下表是模型本身的倾向，不是设备上的样子（设备 5/33 段、运行时回放 048 4/33、054 5/33，每段 ≤58 字）。

| 模型 | 幻觉片段里的复读输出 | 对照片段 |
| --- | --- | --- |
| base Qwen3-ASR-1.7B | 6% | 0% |
| 9.26 版本（34479） | 49% | 0% |
| 10.28 交付（048 avg3） | 36% | 0% |
| 10.28 版本（054 avg3） | 33% | 0% |

- 和电平无关：背景片段放大 12 dB 仍然复读（42–48%）；把测试者本人清楚的说话衰减 18 dB 不会复读。
- 和 prompt 形态无关：运行时流式模板没有 system 块，输出会变但复读率不变（30% 对 36%）。
- 现有评测集几乎看不到：`asr-benchmark` 全量（253k 条，oracle 分段）054 avg3 只有 0.6/万；鼎桥场景集 scene-asr/scene-ts、`asr-babble-bench` 全量的复读率都是 0～0.03%。**所以这个失效模式是我们的评测盲区。**

结论：复读是 v3 三阶段 SFT 引入的解码退化，和目标说话人、注册音频无关，TS 训练轮次没有修掉也没有加重。

## 三、设备上那 891 个字从哪来

对 33 段按字数归因，参考是两个独立的离线模型（base `Qwen3-ASR-1.7B` 与 `FireRedASR2-AED`，各取 2 种边界）：

| 归因 | 段数 | 占设备字数 |
| --- | --- | --- |
| 复读 | 5 | 15% |
| FireRed 两种边界都给空（听不出内容） | 22（含复读共 25） | 60%（含复读 72%） |
| 两个参考都听出语音但内容不一致 | 3（含客户点名的 s1_seg08） | 17% |
| 两个参考内容一致 ≥ 0.3（确有可转写内容） | 3 | 8% |

- 设备文本与 base 在**同一段**上的字符重合度 21%，与**其他段**（随机配对）只有 7%，说明设备输出不是凭空生成，是对该段真实声音的不稳定转写。
- 同一个模型（048）离线在 8 种条件里至少有一种给空的有 13 段，设备上这 13 段都有文字。~~运行时把模型的「空」覆盖掉了~~（10-31 撤回）：13 段里 12 段离线只在 1/8–5/8 的条件下给空，只有 1 段 8/8 都空；运行时回放 048 在其中 5 段给了空。模型在这些片段上本身就处在「写 / 不写」的边界上，设备只是落在了「写」那边，前缀锁定贡献多少没有被单独测出。

## 四、运行时：伪流式定稿强行沿用中间结果

> 10-31 更正：本节最初依据的是本机落后 `origin/main` 650 个提交的 audiollm-go 检出。`origin/main`（`87845d77`，2026-10-20 起）在 `internal/asr/qwenclient/decode.go` 已有：`decodeBudget` 按音频时长给输出上限（96 + 24 token/秒，限制在 128–512）；`repeatedDecode` 检测密集复读（≥96 字且超过 24 字/秒、末尾单元重复 8 次）后把音频对半、不带前缀重新解码。所以下面「前缀体检」对密集复读已经实现；短的附和词串（如 12 个「嗯」）不触发。定稿锁前缀（`decodeWindow` 的 `FinalRollbackTokens`）在 main 上仍然存在。finalizer 调 `ParseModelOutput(raw, false)`，文本层复读修复是关的。

`audiollm-go` 的 `internal/asr/qwenclient/partial.go`：开启 `enable_pseudo_stream` 后，定稿请求会把「上一个中间结果去掉末尾 10 个 token」作为强制前缀（默认 warmup 8 / rollback 5 / final rollback 10）。

后果：

- 定稿继承了中间结果在更短音频上的猜测，同一段音频在不同时序下定稿不同（客户看到的跨次不一致，`cross_run_similarity` 多数为 0）。
- 即使模型在完整片段上决定「没有内容」，前缀也已经写进去了，输出不会为空。
- 要让「听不清就不输出」真正生效，必须同时改运行时，否则训练侧再怎么改都被覆盖。

可选的改法（都在 `transcribeWindow` 里，按代价从小到大）：

| 改法 | 做什么 | 代价 |
| --- | --- | --- |
| 前缀体检 | 锁定前先判一次中间结果是不是复读（同 1–4 字单元连续 ≥ 8 次），是就把 `prefix` 清空，让定稿重新解码 | 最小，只影响已经退化的那一类请求 |
| 定稿不锁前缀 | `final` 分支不拼 assistant 前缀，让定稿在完整音频上自由解码 | 定稿时延变高，定稿与最后一个中间结果的措辞差异变大 |
| 空结果可覆盖 | 定稿先不带前缀解码一次，若为空则输出空，否则再按现在的逻辑拼前缀 | 定稿多一次请求 |

前两条只改 `internal/asr/qwenclient/partial.go`，第三条要改定稿的请求次数约定，属于 audiollm-go 的接口行为，需要那边确认。

**rp 1.1 的真实作用是让模型「多写」，不是「不复读」**：

- 输出净变长：scene-ts 上变长 >3 字的 20 条对变短 7 条（净 +483 字），babble 13 对 1（净 +222 字）。原因可以从代码直接看到：停止符 `<|im_end|>`（151645，`generation_config.json` 的 `eos_token_id` 之一）在每条 prompt 里都出现（user 轮结尾），而 vLLM 的 `repetition_penalty` 连 prompt token 一起惩罚，所以**每一步停止符都被压低**。复读的形状消失了，但模型更难停。
- 代价出现在**该停的时候继续写**：scene-ts 变差样本里模型在机主说完后把干扰人的话也转写了；v12 上变差集中在 `dyn-*`、`real-emilia2-3plus`、`stress-office` 等多说话人/动态切片，误输出率也小幅上升。
- 收益出现在**本该多写却早停**的地方：鼎桥 4 个 79 s 两人长对话场景，默认解码只写出参考字数的 47–57%，rp 1.1 写到 53–61%；按音频位置看片段覆盖率（默认/rp1.1）前 25% 77%/80%、25–50% 54%/57%、50–75% 43%/50%、后 25% 54%/65%，**是整段漏句、中后段最严重，不是截断**。
- **和热词/上下文提示结构性冲突**：vLLM 的 `repetition_penalty` 对「出现在 prompt 里的 token」同样惩罚（`vllm/model_executor/layers/utils.py:apply_penalties` 把 `prompt_mask` 和 `output_mask` 一起传给 `apply_repetition_penalties`），所以 prompt 里列出的热词被主动压低概率 —— 热词命中率掉 1.47 点（给 gold 列表时掉 2.46 点），46/49 个切片变差。这一条不是调参能绕开的。
- **10-31 更正（打分口径）**：上表 CHiME-4、babble、TS v12、警务单说四项的基线 run 的 `summary.json` 是 AmphionEval v1 打分口径，rp 1.1 run 是 v2（英文改用 Whisper 规整等），两边不可比。用 v2 从两边的逐条预测重算后：CHiME-4 7.17→7.31（+0.14），babble 2.08→2.13（+0.05），TS v12 加权 13.07→13.46（+0.39），警务单说 0.313→0.313。原来写的「CHiME-4 −3.81 是语种漂移碰巧改对」撤回，那是打分口径差。另外四项（普通 ASR 全量、热词 v3、鼎桥 scene-asr / scene-ts）两边都是 v2，不受影响。

**结论：rp 1.1 不进交付包。** 八项全量评测里只有鼎桥 scene-asr 一项改善（能解释成「多写」的副产品），而代价是确定的：客户 TS 验收场景 +0.98、TS v12 +0.23（误输出率 +0.09）、普通 ASR 全量 +0.13（31/34 切片变差）、热词命中率 −1.47 点（和 prompt 热词结构性冲突）。收益只在那 33 段客户片段上可见 —— 全量集上连复读都没清干净（普通 ASR 19→12 且新增 4，热词 21→18 且新增 10）。10-09 在会议 SOT 上的结论相同。~~复读和长对话漏句是同一个根因（何时停）的两端~~（10-31 撤回：漏句是中段整句跳过，不是提前停止，和复读不是同一个机制）。

## 七、2026-10-31 复核

上面的分析把力气花在了复读上，复核后有四处要改：

1. **复读不是客户问题的主体。** 设备定稿和 113 上的运行时回放（manifest 里的 `replay_048` / `replay_054`）复读都只有 4–5/33 段、每段 ≤58 字；本文第二节 33% 和「写到 token 上限」是离线整段解码的口径。客户问题的主体是对听不清的背景人声写出不稳定文字：设备 2.84 字/秒，和测试者本人说话（2.3 字/秒）相当；base 离线也写 1489–1879 字，换回 base 不能解决。
2. **rp 是测错了的工具。** vLLM 0.18 有 `repetition_detection`（按重复模式停止，`finish_reason=repetition`，不改 logits，不碰 prompt 里的热词），audiollm-go 的 `amphionv6` 路径已经按请求发送（`cmd/audiollm-go/main.go` 的 `-asr-v6-repetition-detection` 默认开）；运行时的 Qwen 路径另有长度预算 + 密集复读重解码。「只能用 `--override-generation-config` 设 rp」只对 AmphionEval 成立，不是部署的约束。第五节的全量对照结论（rp 不进交付包）不变，但这个问题本来用 10-09 的结论加代码阅读就能回答。
3. **「运行时覆盖了模型的空」撤回**，见第三节更正。模型在这些片段上「写 / 不写」本身不稳定。
4. **「何时停」统一根因撤回**，见第五节更正。

修订后的判断：这 33 段是按「三次输出互不一致」挑出来的，本身就是模型没把握的区域。不改训练就能直接针对它的手段是**按置信度拒识**（例如定稿 token 平均 logprob 低于阈值就不输出），或者在会议角色模式下按角色/注册人过滤；能不能把背景人声和真实的轻声说话分开，现有数据回答不了，需要一次小测：33+4 段客户片段 + 鼎桥 scene-asr / scene-ts 全量（真实安静说话，量误拒）在部署栈上取 logprob。前提是产品口径先定「背景对话不该出字」。

## 八、置信度拒识小测（2026-10-31）

**结论：模型自己的置信度可以把背景人声和真实说话分开，代价很小。** 规则是：转写开头 16 个 token 的平均 logprob 低于阈值，或者输出撞到长度上限且是复读，就把输出置空。

阈值定在 scene-asr 误拒 0.5% 这一档时：
- 客户 32 段有输出的背景片段全部置空，另 1 段本来就是空，4 段对照全部保留；
- 鼎桥 scene-asr、WenetSpeech 真实远场会议、babble 语音三个集合的 CER 基本不变；
- babble 纯背景的误输出从 2.6% 降到 1.2%。

### 做法

- **模型和推理栈**：054 avg3（10.28 版本），部署推理栈（vLLM 0.18.0 服务），配置在 `runs/ts-robust-acp-20261015/configs/eval-054-avg3-confprobe/`。
- **请求形态**：复现 audiollm-go 的定稿请求——user-only prompt（`probes/runtime_user_only.jinja`）、贪心解码、`max_tokens` 按 `decodeBudget` 计算，并返回每个 token 的 logprob（top 20）。
- **数据**：四组全量共 16,207 条。

  | 数据 | 条数 | 期望 |
  | --- | ---: | --- |
  | 客户背景片段 / 对照 | 33 / 4 | 置空 / 保留 |
  | 鼎桥 scene-asr | 4,600 | 保留 |
  | `asr-babble-bench` v3 纯背景 / 语音 | 1,200 / 2,000 | 置空 / 保留 |
  | WenetSpeech test_meeting（真实远场会议） | 8,370 | 保留 |

- **加载和打分**：样本和音频来自 AmphionEval 自己的加载器。打分用 AmphionEval v2 口径，被拒的样本按预测为空计分。

### 结果

- **区分能力**：最好的单个特征是转写开头 16 个 token 的平均 logprob（head16）。用它区分客户背景段和 scene-asr，AUC 是 0.998；和 WenetSpeech 会议集，AUC 是 1.000。
- **复读段要单独处理**：复读段一旦进入循环，模型反而很「自信」，整段平均 logprob 在 −0.06～−0.4，按整段平均算的特征会漏掉它们。开头 16 个 token 时模型仍然犹豫，能抓住大部分复读段。剩下 4 段是「撞上限且复读」，单独加一条规则即可。三个应保留的集合里，没有任何一条输出是「撞上限且复读」。

- **0.5% 档**：scene-asr 被误拒的 22 条，原本的 CER 就有 118%，其中 20 条超过 50%，集中在 PDT 对讲链路和极端噪声场景。这些输出本来就是错的，拒掉以后 CER 反而略降。
- **1% 档**：
  - scene-asr 误拒 45 条，原本 CER 79%；
  - WenetSpeech 误拒 73 条（0.9%），平均 2.9 s，原本 CER 44%。
- **其他特征**：几个特征的完整档位表见结果文件。语种 token 的置信度在 WenetSpeech 上几乎不误拒，但对客户背景段的召回低一些，可以作为备选。

## 九、推理插件与 AmphionEval 全量（2026-10-31）

**结论：插件在 6 个全量集合上和小测一致。** 真实说话的错误率基本不变，被拒的输出原本大多就是错的；背景和非语音上的误输出明显下降。代价集中在两处：川渝方言短句，以及英文 GigaSpeech 带热词列表。

### 插件

- **位置**：open-audio-llm 分支 `feat/asr-confidence-gate`（未 push），文件 `src/open_audio_llm/integrations/vllm/confidence_gate.py`，用 vLLM 的 `--middleware` 挂载，只依赖标准库。部署说明在 `docs/guides/deployment.md`。
- **规则**：和第八节一致。被拒时内容改成模型自己的「无语音」输出 `language None<asr_text>`，`finish_reason` 为 `stop`。
- **前缀**：带前缀续写（audiollm-go 的定稿锁前缀）时，前缀部分用 `prompt_logprobs` 打分。被拒时返回空续写，`amphion_confidence.rejected` 为真，由客户端丢掉前缀。
- **阈值**：−0.831，即第八节 scene-asr 误拒 0.5% 那一档，用环境变量 `AMPHION_CONFIDENCE_THRESHOLD` 传入，不设就启动失败。
- **端到端验证**（`probes/confgate_smoke.py`，客户片段，复现运行时请求形态）：
  - 背景 33/33 不出字，对照 4/4 保留；
  - 前缀续写：对照段按 token 回退 5 个后续写，4/4 通过；背景段带设备定稿的前 8 个字续写，31/33 被拒（11-01 更正，原文写成全部被拒）。没被拒的两段，强制前缀后模型续写变得自信，开头 16 个 token 的平均分在 −0.64～−0.66：
    - s2_seg00 的前缀是 8 个相同的字；
    - s2_seg07 的前缀不重复。
    
    两次运行都是这两段，分数基本相同。真实运行时的前缀是模型自己的中间结果，而中间结果请求本身也经过拒识，所以这里用的是偏坏的情形，实际效果要靠原音回放确认；
  - 判定和离线小测 37/37 一致；
  - AmphionEval 形态的请求（带 system block，`max_tokens` 512）下，有 1 段背景（s1_seg34）仍会出字。
