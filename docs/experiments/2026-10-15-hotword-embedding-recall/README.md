# embeddinggemma-2 热词召回分析与替换可行性

## 结论

**英文：零样本已经超过现网召回；中文：差距很大，必须微调。是否替换取决于微调后中文能否追平，建议按下文"判定标准"决定。**

同口径对比（audiollm-go 的 500 条自检集，万词库，目标对 Recall；音频直接召回）：

| 语言 | 指标 | 现网 RAG | embeddinggemma-2 零样本 | 09-13 候选（历史，未上线） |
|---|---|---|---|---|
| 英文（112 对） | R@1 / R@5 / R@10 / R@50 | 22.3 / 32.1 / 35.7 / 47.3 | 22.3 / 41.1 / 48.2 / 67.9 | 29.5 / 51.8 / 58.9 / 75.0 |
| 中文（52 对） | R@1 / R@5 / R@10 / R@50 | 38.5 / 67.3 / 71.2 / 82.7 | 19.2 / 32.7 / 40.4 / 55.8 | 38.5 / 69.2 / 78.8 / 90.4 |

- 零样本数字用的是"还原词库"（见下文，比真实万词库略小）；补齐到 1 万词后英文 R@50 为 65.2、中文 51.9，趋势不变。
- 样本很小（英文 112 对、中文 52 对，95% 置信区间约 ±9 和 ±13 个点），只能判断量级，不能判断小差距。
- 其余结论：
  - 在 aishell 上，ASR 转写→热词的文本召回，零样本不如仓库现有的拼音规则，但两者互补（见"结果 2"）。
  - 替换在工程上可行：模型原生支持音频，编码延迟小；代价是多一个 570M 模型服务、多一次音频编码。

## 现有方案（对照基线）

训练来源：`github.com/amphionspace/RAG-ASR`（2026-07-08 最新提交）；线上部署与权重记录：`git.amphiondev.com/amphion/audiollm-go`（`docs/MODEL_INVENTORY.md`、`docs/AMPHION_ASR.md`）。

线上链路：音频 → 旧版 AmphionASR-1.7B encoder-only 服务 → 逐帧 adapter 向量 → 每个热词取所有有效帧的最大相似度 → Top-50，再与请求热词合并交给完整 ASR（完整 ASR 自己再编码一次音频，不接收 RAG 的 projector）。因此线上实际是**两次音频 encoder**，不是 RAG-ASR 仓库 README 里描述的共享一次。RAG encoder 权重 SHA-256 `4aa7038f…`，adapter 源 `475539ba…`（OBS：`model/amphion/audiollm/AmphionASR-1.7B/hotword_adapter/pooled/best_adapter.pt`）。

| 项目 | 现有 RAG-ASR | embeddinggemma-2 |
|---|---|---|
| 输入 | 整句音频 | 音频或文本 |
| 音频侧 | **冻结的 ASR audio encoder** + MLP adapter；线上按逐帧向量对每词取最大帧相似度 | 自带 300M 音频 encoder，需单独前向 |
| 文本侧 | 冻结的 LLM embedding + MLP adapter + 注意力池化 | 270M 文本模型 |
| 向量维度 | 512 | 768（可截断到 512/256/128） |
| 可训练部分 | 只训 adapter（小） | 整模型 570M（文本+音频），可选 LoRA |
| 训练损失 | 对称 InfoNCE，4096 个负例，温度 0.07 | 预训练已含音频-文本对齐，未针对热词 |
| 验证 | en-50k / zh-50k 词池，Recall@1…50 | — |

现有方案的一个关键优势：RAG-ASR 仓库设计上让召回与 ASR 共享一次编码（`PROJECTOR_OUT`），但线上实际是召回 encoder 与完整 ASR 各编码一次，所以换成 embeddinggemma-2 并不比现状多一次音频编码（只是换了一个编码器）。

仓库内还有一套文本规则召回（`src/open_audio_llm/integrations/vllm/retrieve_hotwords.py`，拼音滑窗 + 字符重叠 + bigram），用于两阶段评测：先粗识别，再用转写召回热词。

## 实验设置

- 数据：`aishell_hotwords` test，1,806 句有热词，真热词共 2,484 个；其中 416 个在 Qwen3-ASR-1.7B 转写里没出现（"ASR 识别错的热词"，召回最有价值的部分）。
- 候选池：本集热词 1,313 个，再加随机抽取的同语种干扰热词（来自其他中文数据集的热词）。
- 指标：热词级 Recall@K（真热词被召回到 Top-K 的比例）。
- 模型以 bf16 运行（README 要求不能用 fp16）。音频评测用 text+audio 配置（`vision_config=None`）。

## 结果

### 1. 零样本：音频 query vs ASR 转写 query（embeddinggemma-2，aishell）

| 候选池 | query | R@1 | R@5 | R@10 | R@20 | R@50 |
|---|---|---|---|---|---|---|
| 1,313 | 音频 | 0.204 | 0.398 | 0.489 | 0.579 | 0.680 |
| 1,313 | ASR 转写 | 0.587 | 0.877 | 0.922 | 0.951 | 0.972 |
| 11,313 | 音频 | 0.124 | 0.253 | 0.316 | 0.382 | 0.482 |
| 11,313 | ASR 转写 | 0.561 | 0.817 | 0.877 | 0.914 | 0.945 |
| 51,313 | 音频 | 0.085 | 0.164 | 0.207 | 0.261 | 0.343 |
| 51,313 | ASR 转写 | 0.506 | 0.754 | 0.816 | 0.856 | 0.903 |

通用 embedding 按语义对齐，热词召回需要按发音/字形对齐，所以零样本音频召回差，这在预期之内；需要微调才能用。

### 2. 文本召回：embeddinggemma-2 vs 仓库现有拼音规则（aishell，ASR 转写为 query）

| 候选池 | 方法 | 全部 R@5 | 全部 R@10 | ASR 识别错的 R@5 | ASR 识别错的 R@10 |
|---|---|---|---|---|---|
| 1,313 | embedding | 0.877 | 0.922 | 0.733 | 0.793 |
| 1,313 | 规则 | 0.979 | 0.984 | 0.877 | 0.904 |
| 1,313 | 两者并集 | 0.988 | 0.992 | 0.928 | 0.954 |
| 11,313 | embedding | 0.817 | 0.877 | 0.635 | 0.695 |
| 11,313 | 规则 | 0.966 | 0.980 | 0.801 | 0.877 |
| 11,313 | 两者并集 | 0.981 | 0.987 | 0.885 | 0.923 |

说明：
- 规则召回只返回得分超过阈值的词，所以 R@10 之后基本不再增长（上限约 0.984），这是它的设计，不是 K 不够。
- "并集"取两者各自 Top-K 的合并，列表长度最多是单方法的两倍，不是等长对比。
- 规则召回的耗时随词池线性增长：实测 1k 词池约 50 ms/句（单核，纯 Python），按此外推 1.1 万词池约 0.5 秒/句；embedding 是一次矩阵乘，量级差很大。

### 3. 延迟（A800，卡上有其他任务，数字偏保守）

**单请求**（batch=1，顺序请求，不含排队；波形 → 特征 → 音频编码 → 对 1 万词库打分取 Top-50；bf16；500 条自检集，平均 5.8 s；3 号卡，利用率约 65%）：

| 指标 | p50 | p95 | p99 |
|---|---|---|---|
| 端到端 | 98.6 ms | 118.2 ms | 131.0 ms |
| 其中 CPU 预处理 | 4.6 ms | 11.4 ms | — |

- 对 1 万词库的打分（矩阵乘 + Top-50）不到 1 ms，词库大小基本不影响时延。
- 按音频时长：0–3 s p50 91 ms；3–6 s 92 ms；6–10 s 101 ms；10 s 以上 112 ms，随时长增长很慢。
- 同一批请求在 0 号卡（利用率 99%）上 p50 约 100 ms、p95 137 ms，说明对卡的占用不敏感，瓶颈不是算力争抢。

**批量**（3–6 s 的句子，每批的 p50 耗时）：

| 批大小 | 1 | 2 | 4 | 8 | 16 | 32 |
|---|---|---|---|---|---|---|
| 每批耗时（ms） | 96 | 104 | 119 | 136 | 205 | 325 |
| 摊销（ms/句） | 96 | 52 | 30 | 17 | 12.8 | 10.2 |

批大小从 1 到 8，耗时只增加约 40 ms，说明单请求约 85 ms 是与批大小无关的固定开销（很可能是 kernel 启动和 Python 调度，没有做过 profiling 确认）。因此：

- 若线上每个请求单独编码，约 100 ms。
- 若能做微批（等 5–10 ms 凑 4–8 个请求），单请求时延约 120–140 ms 但吞吐高 5 倍以上。
- torch.compile / CUDA graph / TensorRT 理论上能降低固定开销，**没有试过，不能当作已知收益**。

**对照现网**（audiollm-go 记录，共享 GPU，样本很少，不能当 SLA）：

| 项目 | 数值 | 来源 |
|---|---|---|
| RAG encoder-only 请求 | 28–49 ms（4 个单请求） |   audiollm-go `amphion-v6-20260911/rag-chain.md` |
| 召回（Go local，CPU，含首次建池） | 平均 114 ms，p50 95 ms，p95 270 ms（500 条顺序调用） |   audiollm-go `amphion-20260913/rag-recall/README.md` |
| 热词池编码（embeddinggemma-2） | 约 0.25–0.30 秒/千词，离线一次 | 本分析 |

粗略判断：embeddinggemma-2 的单请求编码（约 100 ms）比现网 RAG encoder 请求（28–49 ms）慢约 2–3 倍；但它把"编码 + 打分"合到一个 GPU 请求里，对万词库打分几乎免费，而现网召回环节另有约 95–114 ms 的 CPU 召回耗时。两边的端到端对比需要在同一台机器、同一并发下实测，这里没有做。

### 4. 与现网 RAG 同口径对比（audiollm-go 自检集）

协议沿用 audiollm-go `docs/archive/evaluations/amphion-20260913/rag-recall`：500 条自检集（23 个子集，英文 174、中文 326）、每种语言约 1 万词库、用"参考文本与词库交集"作代理标注（101 条音频、164 个目标对：英文 112、中文 52）、按目标对算 Recall@K。现网和 09-13 候选的数字直接取自该目录的 `targets.jsonl` / `go-local-targets.jsonl`；embeddinggemma-2 在同样的音频和目标对上本地计算。

| 语言 | 方法 | 词库 | R@1 | R@5 | R@10 | R@50 |
|---|---|---|---|---|---|---|
| 英文 | 现网 RAG（音频） | 9,984 | 22.3 | 32.1 | 35.7 | 47.3 |
| 英文 | 09-13 候选逐帧评分（音频，历史） | 9,984 | 29.5 | 51.8 | 58.9 | 75.0 |
| 英文 | embeddinggemma-2 零样本（音频） | 还原 7,084 | 22.3 | 41.1 | 48.2 | 67.9 |
| 英文 | embeddinggemma-2 零样本（音频） | 补齐 9,984 | 21.4 | 38.4 | 46.4 | 65.2 |
| 英文 | embeddinggemma-2 零样本（参考文本） | 还原 7,084 | 32.1 | 49.1 | 56.3 | 75.9 |
| 中文 | 现网 RAG（音频） | 10,087 | 38.5 | 67.3 | 71.2 | 82.7 |
| 中文 | 09-13 候选逐帧评分（音频，历史） | 10,087 | 38.5 | 69.2 | 78.8 | 90.4 |
| 中文 | embeddinggemma-2 零样本（音频） | 还原 8,841 | 19.2 | 32.7 | 40.4 | 55.8 |
| 中文 | embeddinggemma-2 零样本（音频） | 补齐 10,087 | 19.2 | 28.8 | 40.4 | 51.9 |
| 中文 | embeddinggemma-2 零样本（参考文本） | 还原 8,841 | 40.4 | 65.4 | 75.0 | 88.5 |

**词库口径说明（重要）**：真实的 `en-10k.txt` / `zh-10k.txt` 在本机和 OBS 都没找到。我用现网 RAG 在 500 条上返回过的所有 Top-50 词（都是真实词库成员）加上全部目标词还原了词库（英文 7,084、中文 8,841，约占 71%–88%）；"补齐"是再用本地同语种热词随机补到约 1 万。还原词库含现网的"易混淆词"，随机补齐的词更容易区分，所以两种口径大致是上下界，不是原词库。

**09-13 候选**是已验收后回退的历史版本，不代表当前线上；放在这里只是说明"同一套 RAG 架构在逐帧评分、重新配套后能做到多高"，作为参考上限。

**读数**：
- 英文：零样本在 R@5 以上全面超过现网（R@50 约 +18–21 个点），R@1 持平；低于 09-13 候选。
- 中文：零样本在所有 K 上都远低于现网（R@50 约 -27–31 个点）。同一批句子用**参考文本**当 query，中文 R@50 就到 88.5，说明短板在音频侧对齐，不在词表示。
- 零样本英文好、中文差，与预期一致：模型预训练中英文音频-文本对齐远多于中文。

## 可行性评估

**能做的（风险低）**
- 数据：训练用热词标注已有。中文：aishell 3.9 万句、magicdata 8.4 万、aidatatang 4.7 万、aishell3 2.4 万、commonvoice_zh 2.1 万；英文：commonvoice_en 64.8 万句。音频清单目前确认有 aishell、commonvoice_zh、magicdata、thchs30、aidatatang；英文训练音频清单和 aishell3 的音频路径没有核对。
- 训练脚本：RAG-ASR 的 `dual_tower.py` / `train.py` 已有对称 InfoNCE、负例池、验证流程，换塔即可复用，不需要新写损失。
- 推理：延迟小；热词向量可离线缓存；768 维可截断到 256 而几乎无损（官方说明）。

**要付出的代价（风险中）**
- 模型服务：现网已有独立的 RAG encoder 服务；新方案是把它换成一个 570M 的 embeddinggemma-2（只加载 text+audio），部署形态相近，但需要新的 native/Go 召回对接（现在 Go 侧按逐帧向量打分，embeddinggemma-2 是整句向量）。
- 训练参数量是现有 adapter 的几个数量级，需要真正的微调流程（LoRA 或解冻），也要注意 bf16。
- 如果走"文本 query"路线，需要先出一遍粗识别，会增加一次解码延迟；这正是现有音频召回避免的。

**未知项（风险高，决定去留）**
1. **现网基线只有自检集上的数字**：来自 audiollm-go 的历史验收记录（万词库、代理标注、样本小）。现网 adapter 权重本机没有，没法在 aishell、zh-50k 等其他数据上重算同口径数字。
2. **微调后中文能否追平**：零样本中文 R@50 只有 52–56，现网 82.7，能否追上只能靠试验回答。
3. **大词池稳定性**：aishell 上从 1.3k 到 5 万，零样本音频 R@5 从 0.40 掉到 0.16，微调后需要在 zh-50k / en-50k 上验证。

## 判定标准（基于上面的数字）

评测协议：自检集同口径（上表）为主，再在更大的验证集上复核。自检集样本小，只能作为门槛，不能用来判断小差距。

| 门槛 | 标准 | 当前零样本状态 |
|---|---|---|
| 不回退（替换的最低要求） | 英文、中文在 R@1/5/10/50 上都不低于现网：英文 22.3 / 32.1 / 35.7 / 47.3，中文 38.5 / 67.3 / 71.2 / 82.7 | 英文满足；中文全部不满足 |
| 目标（值得替换） | R@50 不低于 09-13 候选：英文 ≥ 75.0，中文 ≥ 90.4；R@5 英文 ≥ 51.8、中文 ≥ 69.2 | 英文 R@50 差 7 个点；中文差 34 个点 |
| 统计可信度 | 自检集差距小于约 9（英文）/ 13（中文）个点时，必须用 zh-50k、en-50k 验证集或带真实热词标注的数据（如 aishell、CommonVoice）复核 | 需要补 |
| 大词库稳定性 | 词库 5 万时，R@50 相对 1 万的下降不超过 10 个点（零样本 aishell 文本召回 1 万→5 万约降 4 个点，音频召回降得更多） | 音频需验证 |
| 延迟 | 召回编码 + 打分的单请求 p95 不高于现网 RAG（encoder 28–49 ms + CPU 召回 p50 95 ms），且不引入排队 | 单请求 p50 99 ms / p95 118 ms，需靠微批或编译优化，且要在同机同并发下复测 |
| 工程成本 | 召回侧需接入整句向量打分与新缓存格式（现为逐帧向量）；热词向量缓存按新模型重建 | 需评估人力 |

解读：
- 英文已经不输现网，替换的主要价值在中文能否微调到位；中文差距最大，训练的重点放在中文音频—热词对齐。
- 如果微调后中文仍低于现网，可退而求其次：只替换英文召回，或把 embedding 作为拼音规则召回/现网 RAG 的补充（文本路线的并集在"ASR 识别错的词"上提升明显）。

## 复现

脚本在 `scripts/`，结果在 `results/`。运行环境用 `oal-score`（transformers 5.19，torch 2.14），另需 `sentence-transformers>=6.1`、`pillow`、`torchvision`、`pypinyin`；分析时这些装在临时目录并通过 `--pkgs` 传入，没有改动共享环境。

```bash
python scripts/compare_rule_vs_embed.py --pkgs <pkgs> --asr-json results/asr_aishell_qwen3asr1.7b.json \
  --retrieve-py src/open_audio_llm/integrations/vllm/retrieve_hotwords.py --out results/rule_vs_embed.json
python scripts/audio_zeroshot.py --pkgs <pkgs> --asr-json results/asr_aishell_qwen3asr1.7b.json \
  --out results/audio_zeroshot.json
# 需要先用 ab pull 取自检集：anfeiweng-audiollm-resource:ascend-model-testdata/delivery-test-data/selfcheck/asr_selfcheck_zh_en_uniform_500_20260703/
python scripts/selfcheck_baseline_compare.py --pkgs <pkgs> --audio-root <selfcheck 目录> \
  --rag-recall-dir <audiollm-go>/docs/archive/evaluations/amphion-20260913/rag-recall \
  --out results/selfcheck_vs_deployed_rag.json
```

`results/asr_aishell_qwen3asr1.7b.json` 是用 Qwen3-ASR-1.7B 对 aishell test 中 1,806 条有热词的句子转写的结果（语言固定为 Chinese）。

已知局限：
- 自检集对比用的是还原词库（见结果 4），不是真实万词库；样本只有 164 个目标对，且是代理标注。
- 干扰热词是同语种随机抽样，不是难负例，真实难度可能更高。
- 音频和 ASR 对比只做了 aishell（朗读语音）；其他数据集没有可用的测试音频，只有文本结果（见会话中的多数据集表，未纳入本目录）。
- `compare_rule_vs_embed.py` 在出结果后只改了"并集"一行的命名和一处冗余表达，结果文件同步改名，计算逻辑未变，未重跑。
