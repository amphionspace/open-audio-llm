# 面向 ts-asr-benchmark@v7 的下一轮训练数据设计

状态：**方案，未执行**。数字没有标「提议」的来自实测；标「提议」的是设计值，执行前需要确认。

评测对象：011 的 checkpoint-7000（第 7000 步，学习率还没衰减完），对照 checkpoint-34479。评测集 `open-audio-llm/ts-asr-benchmark@v7-20261017`（196 列，8 个子集），服务口径同 `baselines/`。014 训练到 15000 步后要再测一次，下面的权重在那之后定稿（见「执行顺序」）。

## 结论

checkpoint-7000 在「该拒的」上大幅变好，但换来了两个新问题，都有明确的数据原因：

1. **目标说话人说多句时，漏掉整句。** 目标只说一句时，删除率不变（10.9%），插入率从 12.5% 降到 1.4%，是纯收益；目标说两句及以上时，删除率从约 10% 涨到 26%–34%。训练数据里目标说两句的场景只占约 1.3%（见下），说三句以上的没有。
2. **真实会议里，注册人不在场时误输出翻倍**（6.9% → 15.6%）。误输出的是窗口里别人的原话；注册音频取自同一场会议的另一个人（同一个房间、同一套麦克风），训练里的这类负样本只占约 1.5%。

另有两处相对 34479 变差、数据原因较明确：4 个以上说话人同时说的缺席场景（babble、`abs-k4`），以及目标单独说短句（`solo-mid`）。

下一轮数据按这四件事补，保持 TS 50 / ASR 33 / 热词 17 的总配比不变，只重分配 TS 内部。

## 二、四个问题的证据与数据原因

### 问题 1：目标说多句时漏句

把目标在场的合成样本（注册音频、进场离场、环境、远场四个子集，共 7,680 条）按目标说几句拆开，用字符级编辑距离分解错误：

| 目标语句数 | 样本 | 删除率 34479 → 7000 | 插入率 34479 → 7000 |
| --- | ---: | ---: | ---: |
| 1 句 | 4,013 | 10.9% → 10.9% | 12.5% → **1.4%** |
| 2 句 | 2,661 | 11.6% → **34.1%** | 3.1% → 0.5% |
| 3 句及以上 | 1,006 | 7.6% → **26.5%** | 0.9% → 0.2% |

- 漏的不是某一句：2 句样本里第 1 句和第 2 句的删除率分别从 11.8%/11.4% 涨到 29.5%/38.3%，3 句样本里三句都涨到 23%–30%。模型倾向于只输出一段。
- 示例（`enroll-clean-pos:0037`）：参考「死亡人不能作为被告」+「关于苹果手表的各种段子充斥各种社交网络平台」，输出只有前半句。
- 真实对话里目标在场没有这个问题（删除率 6.4% → 4.0%），因为真实窗口里目标的话是连续的一段。问题只出在「目标几句话被别人打断」的合成场景，评测里这类占在场样本的 48%。
- 训练覆盖：`ts_scene_pool` 里只有 `alternate` 模式目标会说两句（35% 的场景 × 40%，约 14%），`burst`、`short` 都只有一句，没有三句以上；`aishellmix`/`librimix` 的单人混合也是一句。折算到全部训练样本约 1.3%。

### 问题 2：真实会议里目标缺席时误输出

| 来源 | 1 人 | 2 人 | 3 人及以上 |
| --- | ---: | ---: | ---: |
| AISHELL-4（34479 → 7000） | 8% → 26% | 16% → 30% | 12.5% → 33.9% |
| AliMeeting | 2% → 6% | 2% → 10% | 10.7% → 26.8% |

- 抽查 5 条 AliMeeting 误输出：输出都是窗口里另一位说话人的原话（逐字转写）。这类窗口里的所有人和注册人都是同一批会议参与者，声学条件相近。模型在合成数据上学会拒绝，没有迁移到这种「会议里的另一个人」。注册音频与窗口是否取自同一场会议，只抽查了少数几条，没有逐条核实。
- 训练覆盖（已核实）：会议类 `train_neg`（`turn-taking-20261014`，alimeeting_sdm、aishell4、ami_sdm、chime6、magicdata_ramc）合计权重 1.5，占全部训练样本约 1.5%；注册人确实取自同一场录音，但**窗口里总有 2–3 个说话人**，没有「窗口里只有另一个人在说话」的 1 人窗口，而评测里误输出最高的正是 1 人窗口；另外它们读 8 路麦克风的平均，评测读第 0 声道。
- 合成的相近声音负样本（`hard-20261016`）把 `abs-hard` 从 47.5% 降到 20.0%，有效；但它们没有真实房间和麦克风的一致性。

### 问题 3：多人同时说话的缺席场景变差

| 列 | 34479 | checkpoint-7000 |
| --- | ---: | ---: |
| `nonspeech-babble`（5–20 人同时说） | 30.8% | **55.0%** |
| `abs-k4`（缺席，4 个干扰人） | 24.2% | 43.3% |
| `abs-mid2-k2`（缺席，3–6 秒，2 个干扰人） | 29.2% | 45.0% |

- 同时间，`nonspeech-crowd`、`nonspeech-events` 等从 57%–68% 降到 7% 以内，说明「没有人声」学得很好，退化集中在「有人在说话，但不是注册人」且人数多、声音混在一起。
- 训练覆盖：在线混合的缺席样本干扰人数是 0–3 个（`absent_interferer_probs = 0.2/0.4/0.3/0.1`，下标就是人数），3 个的只占 10%，4 个以上的没有；场景池的缺席场景虽然最多有 6 个其他说话人，但只占 TS 的 9%。训练的 `noise_sources` 里没有 `babble_noise_synth`。该数据集已登记了 `zh_train`、`en_train` 划分，评测用的 babble 取自测试划分的 34 位说话人，与训练划分互不重叠，可以直接用于训练。

### 问题 4：目标单独说短句略变差

`solo-mid`（只有目标说 2–6 秒）CER 4.5% → 9.0%，是控制指标，说明压低误输出时有一部分代价落在短句上。业务回归「目标在场」只有 2 条，18% → 73% 没有统计意义，只作提醒。训练里「只有目标、没有干扰人」的样本只占单人混合的 20%（约占全部训练样本 2.2%），没有按短句单独设置；本轮方案把单人混合下调后这部分会变少。

### 新增数据

| 项 | 做什么 | 规模（提议） | 对应的 v7 列 |
| --- | --- | --- | --- |
| **A. 多句目标场景** `ts_scene_pool@multi-20261017` | 评测基础场景的做法：目标说 2–5 句（0.4/0.3/0.2/0.1），1–4 个其他说话人（0.3/0.3/0.25/0.15）各有一条轨道和自己的停顿档（0.2–1、0.2–1、1–3、2.5–6 秒，与评测一致），轨道在加载时随机错开，所以目标的话会被别人打断也会被盖住；总长以最大停顿计不超过 32 秒；参考文本是目标各句按时间顺序拼接。约 26% 的记录是**缺席孪生**：同一批语句和停顿，目标的语句变成另一个干扰人的，注册人换成场景外的另一位（一半随机，一半取目标的近邻声音），目标为空 | zh 12 万、en 4 万 | 进场离场与缺席、注册音频、环境与底噪、远场与房间的在场列；`abs-*` |

构造要点：

- **孪生成对是整个设计的核心。** 同一条混合音频同时出「在场（有转写）」和「缺席（为空）」，模型只能靠注册音频的声音去判断，没法靠「场景长什么样」走捷径，也避免这一轮的改动把多句漏句和误输出再次互相换来换去。
- 目标说话人和其他说话人沿用 `ts_scene_pool` 现有规则：来自带真实说话人标签的语料的**训练划分**，彼此不同。
- B 是真实录音，不做在线混合，只在已有的多说话人窗口记录上换注册音频；干扰与噪声沿用在线增强。

### 与评测集互不重叠的核对

- 说话人：A、C 用训练划分说话人；评测说话人只来自官方测试划分。
- 真实会议：B 只用各语料的训练划分；评测用官方测试划分，场次不同。
- Babble：评测的 babble 取自 34 位测试说话人，训练用 `zh_train`/`en_train`，已登记为互不重叠。
- DNS5 噪声与房间响应：沿用上一轮已排除评测片段的训练划分。
- 每项新数据构建后，沿用 `check-registration --require-record-index` 并抽样核对说话人和录音 ID 与 v7 评测集不相交。

## 五、风险

- **checkpoint-7000 不是终点。** 014 训到 15000 步，学习率衰减到 1e-6，漏句可能部分恢复。所以先测 014 的最终模型，再定权重；A、B、C 的构建不依赖这个结果，可以现在就开始。
- **来回摆动。** 这一轮就是「拒绝」和「漏句」的互相换。孪生成对和保持项是对策，但不能保证；若 A 加上去后误输出明显回升，优先调低缺席孪生的比例，而不是砍 A。
- **下调的三项。** 单人混合和场景池 v2 压低以后，无人声、短片段缺席可能回弹。验收里已列入不退化项；若回弹，把场景池 hard 部分先补回来。
- **B 的规模取决于说话人数。** 每场会议的说话人数少（AliMeeting 约 2–4 位，AISHELL-4 约 4–6 位），可选的「窗口外说话人」有限，先盘点再定规模。
- **多句目标的参考文本是拼接。** 评测集也是这样构造的，但真实对话里目标的多句通常有语义关联，这里没有；真实对话在场列（已变好）作为保持项监控。
- **没有做的**：对外部论文和开源做对比调研；没有验证 A 的多句场景在 3–20 秒注册音频和 32 秒场景下的批次显存占用。

## 六、执行顺序

1. 014 训完（约 3 小时）后，在 v7 全量上测最终模型，作为本方案的基线，并重新核对问题 1–4 是否仍然存在。
2. 同时开始数据侧：扩展 `scripts/ts_robust/build_ts_scene_pool.py` 做 A；盘点 B 的可用窗口和说话人；改配置做 C；检查 D 的现有数据。
3. 每项数据登记到 audio-data-contract（worktree + PR），建 Lance 记录索引，通过 `check-registration --require-record-index`。
4. 新建训练数据配方和配置（不带 `reset_catalog_sampler`，数据变了所以签名变，需要重置位置；起点用 014 的最终 checkpoint），预检不再写进配置，改由缓存命中保证速度。
5. 训练、周期保存，用 checkpoint 在本机 vLLM 上评测（v7 全量），按第四节判定。

## 十一、022/023 在第 6581 步失败：一条转写异常的训练记录（2026-10-18）

**结论：** 022、023 在 08:14 UTC 同时失败，原因是 emilia2_mix 的一条记录，转写是 17053 个字符的重复循环（“Let your dream take you.” 约 700 遍），对应 24 秒音频，编码后 4692 个 token，超过 `max_length` 2048。加载器遇到超长行直接抛 `MaxLengthError`，一个 DataLoader worker 报错就让整个训练退出。两个训练数据种子相同，所以在同一步一起失败。不是节点或网络问题；两边都留有 checkpoint-6000。

**定位：** 在 CPU 上重放采样器（world_size 8、rank 0），失败那一批是第 13164 个批次（DataLoader worker 0 的批次），其中 `emilia2_mix:train_2spk` 的 `e30814da3f3c10b9_L0001#1` 的消息长度是同批其他样本的 50 倍。

**范围：** 扫描配方里全部数据源（每个数据集版本的每个划分）的 Lance 索引（`scripts/scan_text_anomalies.py`，结果在 `configs/bad-text-records/`）。超过 1000 字符的转写只有 emilia2_mix 的 17 条（2spk 10、3spk 7），全部是幻觉循环、每秒超过 25 字符；其余数据源没有。按 60000 步估算，每次训练会抽到这类记录约 1.4 次，所以之前 016 等只跑 15000 步的训练没抽到，不是数据变好了。

**处理：**
- 新配方 `train-data-v7set3.yaml`（`scripts/make_recipe_v7set3.py` 由 v7set2 生成）：在 `exclude_records` 里再排除 emilia2_mix 每秒超过 20 字符的 23 条，和 emilia2_short 英文每秒超过 30 字符的 131 条（文字比语音能说的还长，是标注错位）。排除名单写在 run 目录的新文件里，`ts_asr_real/source/v2-20261013` 下原有名单属于另一轮，没有改。
- 数据种子换成 20261019：22/23 已按 20261018 的样本流训练到第 6000 步，续训不重放。
- 续训：`train-1node-v17.yaml`（022 的 checkpoint-6000，attempt 024，pt-55u9s13u）、`train-1node-v18.yaml`（023 的 checkpoint-6000，attempt 025，pt-76nsav7r）。模型、优化器、调度器、步数 6000 恢复，采样器重置，总步数仍 60000。
- 08:27 先提交了两个普通名字的占位任务保住两个节点，08:41 提交续训任务后停掉占位任务，续训两个任务在几秒内 RUNNING。

**剩余风险：** 加载器仍然不会跳过超长行（swift 自带的 LazyLLMDataset 会，CatalogSwiftDataset 没有）。本次扫描覆盖了转写长度，没有覆盖其他会让一行超长的情形（例如异常的热词列表）。建议另开一个小 PR，让加载器遇到超长行时重抽样并记数，而不是退出训练。

### 十二·补 采样器实际喂给模型的是什么，以及对第十二节的更正（2026-10-18）

用 `scripts/plan_census.py` 重放第 0 个 epoch 的批次计划（rank 0，world_size 8，新旧配方各一份）。

- **各数据源的样本数严格按权重：** 重放采样每 2000 条为一个窗口，每个数据源在窗口内拿固定名额，源内是打乱后不放回循环；实际占比与权重的总偏差只有 1.1%。
- **但每一步并不是均匀混合：** 窗口内的样本按时长排序后切批，一个微批的 12 条样本时长几乎相同（最长/最短的中位数 1.02），来自约 8 个数据源；一个优化步的 16 个微批总开销相近，步与步之间再打乱。所以短于 10 秒的批里带目标的样本只占 12%–30%（其余是纯 ASR、热词），15 秒以上几乎全是带目标的样本。
- **更正：** 第十二节给出的“缺席占比从约 16.5% 升到约 34%”分母漏了离线轮流说话/对话集（旧 36.7、新 29.2），算错了。按全部带目标的数据源折算，缺席（目标输出为空）占比是 **13.3%（v5）→ 19.4%（v7set2）**；在基准场景所在的时长段（含 3 秒注册音频约 10–15 秒），14.3% → 21.9%。方向没变，幅度只有一半不到，单凭这个很难解释目标在场输出为空从 3.5% 升到 23%–29%，只能算候选原因之一。
- **步间波动：** 每个优化步里 rank 0 的 24 条样本中，预期缺席占比 v7set2 为 0.196 ± 0.098（10 分位 0.05，90 分位 0.32），v5 为 0.134 ± 0.078。

- 回放采样器（seed 20261020，rank 0）看批次组成：15000 → 25000 步每 1000 步各来源占比的标准差只有 0.07–0.35 个百分点（真实窗口 4.5–4.9%，多句场景池 8.4–8.9%，hard 池 2.8–3.1%，在线单目标 11.3–11.7%，平均时长 15.6 秒），并没有慢变化；所以摆动不是某一段数据的来源比例不同造成的。
- 两条线同向说明是同一批样本顺序造成的共同扰动（两条线同一数据种子），但具体机制没找到。摆动幅度（空输出 ±4 个点）比评测噪声（约 1 个点）大得多，说明单个 checkpoint 的好坏有很大运气成分。
- 25000 → 35000 新增空输出的样本分布很广，没有集中在某个条件；相对更多在较短参考句（<25 字）和较长注册音频（5–8 秒翻倍，8 秒以上最高）。

### 十三·十一 相对 34479 的回退到底在哪里，怎么解决（2026-10-19）

**回退是什么：** 以 avg3 / 028@17k 为例，目标在场输出为空约 9–10%（34479 为 7.1%），solo-mid 字错率 11–15%（4.5%），1 句目标空输出 13–16%（9.5%），业务反馈集 2 条短在场样本仍错；同时真实对话缺席贴着 8% 门槛。

**一、solo-mid 的回退全是“弃权”，不是识别变差。** solo-mid（120 条，中位参考 6 个字、片段约 4.7 秒）的字错率拆开：34479 删除 0.2% / 替换 3.5%；avg3 删除 7.2% / 替换 3.5%；028@17k 删除 12.2% / 替换 2.5%；026@58k 删除 18.0% / 替换 2.2%。输出非空时识别质量不比 34479 差（替换更低），差的只是该不该输出。参考 ≤6 个字的最严重（12–28% 空输出）。回退集中在“目标单独说话”和“轮流说话”的条件：dyn-solo 0 → 11.7–16.7%，dom-solo-traffic/music 1 → 13–20%，floor-none 0 → 7%，dyn-alternate-k4 1.7 → 17.5–23%，enroll-short1 0.7 → 15%；而 34479 差的“目标很轻/很短/被盖住”（dyn-short-k3 52.5 → 10%，level-q20 26.7 → 13%，nearfar-3plus 41 → 5–9%）反而好很多。模型从“有人说话就转写”变成“证据不够就弃权”。

**二、全局调弃权偏置换不来便宜的召回。** 弃权决策只是 `language` 后面的一个 token（` None`，id 2240，对比 ` Chinese` 8453、` English` 6364），可以在推理时用 `logit_bias` 调。对 026 最后三点平均（tail3）在 900 条在场 + 600 条合成缺席 + 567 条真实缺席上扫偏置：

| 偏置 | 在场输出为空 | 在场字错率 | 合成缺席误输出 | 真实缺席误输出（会议语料 / emilia2） |
|---|---|---|---|---|
| 0 | 13.0 | 22.7 | 2.2 | 8.1（7.0 / 11.0） |
| −1 | 9.2 | 20.8 | 3.2 | 17.8（12.6 / 31.6） |
| −2 | 6.6 | 19.5 | 6.0 | 27.9（18.7 / 52.3） |

偏置 −1 把空输出降 3.8 个点，却让真实缺席误输出翻倍，emilia2 对话从 11% 涨到 32%。所以真实对话缺席（≤8%）这个门槛，让“推理时放松弃权”这条路走不通；要改善的是真实数据上的分辨能力，不是全局先验。这也说明模型在两类输入上的工作点不同：合成输入偏弃权（缺席误输出 2–3%、在场空输出 10%+），真实输入偏输出（emilia2 缺席 11%；nearfar 3 人以上近场注册 + 近场混合的缺席 27–30%，比 34479 的 18% 还高）。

**三、训练数据里对应的缺口（已核对配方）：**

1. 短目标：v5 里有 `ts_scene_pool@v2`（alternate / burst / short 三种场景，占 6%），v7set 起整体换成 multi，v2 被拿掉。轮流说话（alternate）和 1–3 秒短目标因此没有在场监督；solo 的目标说话人本身又没有“短于 3 秒”的纯在场样本。
2. 真实数据覆盖：真实窗口 B（ts_real_train v1）只有 alimeeting / aishell4 / ramc，占 4.8%；Emilia2 只有离线的 2 人 / 3 人窗口，没有“只有另一个人在说话”的窗口（builder 文档里明说），对应 real-emilia2-1spk-neg 缺席误输出 8% → 22–26%；B 只读远场阵列的第 0 路麦克风，没有 AliMeeting 近场（头戴）窗口，也没有近场 / 远场交叉的注册与混合，对应 nearfar-3plus-en-mn（近场注册 + 近场混合，3 人以上）缺席 18% → 27–30%（nearfar 是 AliMeeting 的近远场组合，`en/ef` 是注册近场 / 远场，`mn/mf` 是混合近场 / 远场；此条原因是推断，尚未核对 B 的通道）。
3. 难负例比例偏高：multi 的缺席孪生一半取近邻声音（占混合 13%），hard 池 56% 是近邻声音缺席，合在一起约占全部样本的 2.7%（v5 为 1.7%），加上 B 的真实缺席 2.3%，让模型在证据弱的合成输入上更倾向弃权。
4. 已经在 catalog 里、尚未用上：`ts_real_train@v2-20261018`（目标锚定窗口，按重叠比例分桶，剔除了与 dev/test 同说话人的录音）。

**四、方案（按预期收益排序，都是数据侧，不改模型）：**

| 序号 | 动作 | 针对 |
|---|---|---|
| 1 | 配方换 `ts_real_train@v2-20261018`，真实窗口权重 4.8% → 约 9% | 真实缺席分辨 |
| 2 | 新增 Emilia2 的单人窗口（目标单独说 / 只有另一个人单独说，各自成对）和 AliMeeting 近场窗口，进 ts_real_train | real-emilia2-1spk-neg、nearfar 3 人以上缺席 |
| 3 | 把 `ts_scene_pool@v2`（alternate / burst / short）加回约 4%，并新做“目标单独、0.5–3 秒短句”的纯在场池（带随机说话人的同内容缺席孪生） | solo、轮流、短目标的弃权 |
| 4 | 合成难负例减半：hard 池权重 2.85% → 1.4%，multi 的近邻孪生降到 1/3 | 合成输入过度弃权 |
| 5 | 验收按多个 checkpoint 的均值和最后三点平均，不看单点（单点摆动 ±4） | 摆动 |

先做 1 和 5（现成，无需构造），再做 2、3、4。2 和 3 需要新建数据，不占算力节点；028 / 029 的场景池对照约 4.5 小时后出，节点空出再用。

### 十三·十四 下游反馈（2026-10-19）：无标点、首字延迟、目标说话人用例（audiollm-go CI）
