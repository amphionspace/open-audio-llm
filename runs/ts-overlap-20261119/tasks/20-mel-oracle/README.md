# 20 11.17 的输入表示（log-mel）是否丢掉了分离需要的信息

## 要回答的问题

任务 18 证明了重叠音频可恢复，但那里用的理想掩码是在 512 点 STFT（32 ms 窗、8 ms 步长）上做的。AuT 实际看到的是 Whisper 128 维 log-mel（25 ms 窗、10 ms 步长），频率分辨率更粗。如果两个人的声音在 mel 频带里已经混得分不开，那么只改编码器的训练不够，还得改前端。

## 方法

- 样本是任务 18 的 615 条（v12 重叠 ≥ 0.9，有精确的单独音轨）。
- 用 11.17 自己的计算方式，算出混音段的 log-mel：400 点 STFT、160 点步长、128 个 mel 带，按整条音频的最大值截掉 80 dB 以下，再做 (x + 4) / 4。重算结果与模板产生的特征逐点一致（1,845 次最大差 0.0）。
- 用目标人和"其余声音"两条音轨的 mel 能量做掩码，替换 11.17 输入里混音那一段，注册段不动，HF 贪心解码。三种条件：
  - **melcheck**：不加掩码；
  - **melibm**：只保留目标能量更大的 mel 点，其余压到底噪；
  - **melirm**：混音能量 × 目标 /（目标 + 其余）。
- 脚本：[mel_oracle_decode.py](../../scripts/mel_oracle_decode.py)、[mel_oracle_report.py](../../scripts/mel_oracle_report.py)、[run_mel_oracle.sh](../../scripts/run_mel_oracle.sh)。ACP `pt-0vbbz0mo`，8 卡，2026-11-23 02:5x UTC。

## 结果

| 615 条，11.17 转写错误 | 全部 | 1 个干扰人 | 2 个干扰人 |
|---|---:|---:|---:|
| mel 不加掩码（HF） | 14.15% | 10.97% | 16.46% |
| **mel 理想比例掩码** | **6.64%** | 6.36% | 6.84% |
| mel 理想二值掩码 | 20.82% | 11.28% | 27.75% |
| 参照：STFT 理想比例掩码 / 二值掩码（任务 18，vLLM） | 5.76% / 8.09% | 4.91% / 6.24% | 6.37% / 9.44% |
| 参照：去掉干扰人（任务 18） | 6.69% | 5.88% | 7.28% |

- **在 AuT 自己的输入上做理想比例掩码，就能到 6.64%**，和去掉干扰人（6.69%）一样。2 个干扰人时也有 6.84%。
- **mel 频带里被其余声音压住的目标能量只占 7.5%**，STFT 频点里是 6.1%。频率分辨率变粗后，只多了约 1.4 个百分点的目标能量被盖住。
- 理想二值掩码反而更差（20.82%），2 个干扰人时最严重。原因是二值掩码在 mel 图上挖出大片压到底噪的"空洞"，11.17 从没见过这种输入。这说明它对硬掩码造成的失真很敏感，不说明信息丢了：同样是二值掩码，在 STFT 上做完再合成回波形，平滑掉了空洞，就只有 8.09%。

## 结论

- **AuT 的输入表示不是瓶颈。**128 维 log-mel 保留了把目标分出来需要的信息：目标在九成以上能量的 mel 点上占优；在输入上做软的理想掩码，11.17 就能达到干净水平。
- 问题完全在编码器对这些特征的处理，与任务 18 的结论一致。端到端方案可以直接以 mel 域的理想比例掩码作为编码器的辅助监督目标，上限约 6.6%。
- 辅助目标要用软掩码。11.17 对硬掩码造成的空洞很敏感。
