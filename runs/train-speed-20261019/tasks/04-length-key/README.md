# 04-length-key：排序键改成接近实际 token 长度，能省多少

- 输入：030 的数据配方 v7set6、026 checkpoint-25000 的 processor / template（只加载分词器和特征提取器，不加载权重）。
- 方法：
  - `scripts/realized_lengths.py`：按采样器真实顺序（epoch 0 的 mux 流）取前 8000 条，走训练时的在线混合、增强和 template 编码（48 个 CPU 进程，约 17 分钟），记录每条的排序键、总 token、音频 token、有监督 token。
  - `scripts/length_key_sim.py`：按 `packing: sorted` 的切批规则（同槽位、升序、≤12 条、填充后时长 ≤480）用不同排序键重新组批，用实际 token 计算填充。
  - `scripts/length_key_fit.py`：只用采样阶段就能算出的量构造排序键；文本 token 按来源估计，用前 4000 条拟合、后 4000 条评估；每 16 个 batch 组成一个更新步（与 `_balanced_updates` 相同），统计任务组成。
- 进展：attempt 001 完成（2026-10-19），8000 条全部编码成功，无报错。

## 结果

模拟能复现实测：现有排序键模拟出的 token 填充是 23.4%、音频填充 13.9%，029 实测分别是 23.9%、13.8%。

填充来源（窗口 2000）：
- 只按实际音频长度排序，填充仍有 18.7%。所以主要原因不是音频长度，而是文本 token：热词样本的提示有 117–224 个 token（中位 164，占这类样本 token 的 71%），普通 ASR 只有 23–52 个，TS 为 58–126 个。音频时长相近的样本混在同一批里，短文本样本要补齐到长提示的长度。
- 在线混合 TS 的音频 token 数与排序键的比值在 10.1–14.6 之间（其他来源稳定在 13.0 左右），这部分大约占 5 个点。

样本外对比（后 4000 条）：

| 排序键 | token 填充 | LLM token 量 | 更新步任务组成 TV 均值 | 单一任务 >90% 的更新步 |
|---|---|---|---|---|
| 现在（时长上界） | 23.6% | 100% | 0.45 | 0% |
| 音频时长×13.05 + 来源文本中位数 | 16.0% | 91.0% | 0.50 | 20% |
| 音频时长×13.05 + 来源文本线性拟合 | 15.2% | 90.2% | 0.49 | 20% |
| 实际音频 + 来源文本中位数（需提前确定在线混合长度） | 11.0% | 85.9% | 0.50 | 20% |
| 实际总长度（理论下限） | 0.8% | 77.0% | 0.46 | 20% |

后 4000 条只有 20 个更新步，组成比例是方向性的，不是精确值。

## 换算成速度

按单卡计时，文本解码器约占每个 microbatch 时间的 61%（原生）/ 52%（Liger）。
- 简单排序键（来源文本估计）：LLM token 少约 9–10%，每步快约 5%。
- 再把在线混合长度提前确定：少约 14%，每步快约 7–8%。
- 理论下限：少 23%，每步快约 12–13%。

## 结论

- 采样阶段能算出的简单排序键只能省约 9–10% 的 LLM token（每步约 5%）。代价是带长提示的热词样本会聚成独立的更新步：约 20% 的更新步被单一任务占满，现在是 0%。这对训练效果的影响未知，要验证就得做训练对照。
- 剩下的填充来自逐条随机的量（热词个数、转写长度、在线混合的注册音频与前后留白），采样器在不解码的情况下拿不到。要逼近理论下限，需要把这些随机量的抽取提前到采样阶段，涉及采样器与数据集之间的契约，改动面较大。
- 结论：收益不足以抵消组成变化的风险，不建议单独实施。
- 更直接的替代方案：padding-free（把一个 batch 拼成一条序列，用 varlen 注意力）。它不需要改排序和批次组成，就能去掉全部填充计算（约 23% 的 LLM token）。但需要 flash-attn 的 varlen kernel（当前环境没有），Qwen3-ASR 的 mRoPE 位置和音频占位符也要适配，可行性需要单独评估。

证据：`attempts/001/lengths.jsonl`、`sim.json`、`fit.json`、`run.log`。
