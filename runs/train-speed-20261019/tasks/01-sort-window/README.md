# 01-sort-window：排序窗口 2000 → 8000 能省多少填充

- 输入：ts-robust 030 的数据配方 `train-data-v7set6.yaml`（replay 下 `buffer_size` 实际取 `replay.window_samples` = 2000，`packing: sorted`、`accumulation: 2`），8 卡、每卡 12 条。
- 方法：`scripts/batch_plan_stats.py` 用真实采样器（main 9dd548b）生成前 384,000 条样本的全局批次计划，只改窗口（2000 / 4000 / 8000 / 16000），不读音频、不用 GPU。填充按采样器自己的排序键（时长上界）计算；组成按每个优化步（8 卡 × 2 次累积 = 16 个 batch、约 190 条）统计四类任务（在线混合 TS、记录型 TS、普通 ASR、热词）的占比。
- 完成条件：得到各窗口的排序键填充和每步组成。
- 进展：attempt 001 完成（2026-10-19，约 2 分钟）。

## 结果

| 窗口 | 排序键填充 | 每条填充后秒数 | 每步任务占比与全局的偏差（TV 均值 / p90） | 单一任务 >90% 的步 | 每步数据集数 |
|---|---|---|---|---|---|
| 2000 | 0.91% | 16.16 | 0.313 / 0.452 | 0% | 18.5 |
| 4000 | 0.45% | 16.08 | 0.422 / 0.533 | 3.0% | 14.5 |
| 8000 | 0.23% | 16.05 | 0.341 / 0.488 | 0.45% | 17.5 |
| 16000 | 0.12% | 16.03 | 0.336 / 0.489 | 0.60% | 17.5 |

029 实测（第 200 步之后、8 个 rank 合计）：LLM token 填充 23.9%，音频帧填充 13.8%。

## 结论

- 窗口 2000 时按排序键已经几乎没有填充（0.9%）；换到 8000 最多再省 0.7% 的计算，远小于预估的 8–15%。
- 实测 24% 的 token 填充来自排序键与实际长度不一致：排序键是采样器的时长估计，实际长度还受在线混合（注册音频长度、干扰人数随机）、转写与热词提示的 token 数影响。加大窗口解决不了这一部分。
- 加大窗口还让每个优化步的任务组成略偏（TV 0.31 → 0.34，偶有单一任务占 90% 以上的步）。
- 决定：不改窗口。要降低这 24%，需要让排序键更接近实际 token 长度，属于新的设计改动，未在本任务实施。

证据：`attempts/001/plan-stats.json`、`attempts/001/run.log`。
